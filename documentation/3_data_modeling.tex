\chapter{Data Modeling}
\label{chap:data_modeling}

This chapter details the data persistence layer of \textbf{BookSphere}. Given the polyglot nature of the architecture, the data modeling strategy is split between a \textbf{Document-Oriented} approach (\textit{MongoDB}) for content management and analytics, and a \textbf{Graph-Oriented} approach (\textit{Neo4j}) for social interactions and recommendation algorithms.

\section{Data Source and Volume}
To ensure the system was tested against realistic data volumes and complex interaction patterns, we implemented a hybrid data generation strategy using custom automation scripts. The core catalog and foundational rating data are sourced from the \textbf{Amazon Books Reviews Dataset} (providing real-world book metadata and user ratings). 

This real data is a user base of approximately 10,000 active accounts. The generation process automatically populates the polyglot persistence layer:


\begin{itemize}
    \item \textbf{Amazon Books Reviews Dataset ($\sim$5GB):} Provides the core catalog of books and real-world reviews spanning from 1996 to 2014.
    \item \textbf{Book-Crossing Dataset:} Used as a supplementary source for user ratings to increase data \textit{variety} and \textit{volume}.
\end{itemize}

\subsection{ETL Pipeline}
\label{sec:etl_pipeline}
The dataset generation follows a 6-step ETL (Extract, Transform, Load) pipeline implemented in two Python scripts:

\begin{enumerate}
    \item \textbf{Books Merge:} Amazon \texttt{books\_data.csv} and BookCrossing \texttt{Books.csv} are merged by title match. Configuration limits (\texttt{MAX\_BOOKS=20,000}, \texttt{MAX\_REVIEWS\_PER\_BOOK=50}, \texttt{MAX\_USERS=12,000}) control the final dataset size.
    
    \item \textbf{Users Generation:} Users are sampled from both sources, enriched with BCrypt-hashed passwords, randomized emails, and ISO country codes from 50 countries via the \\texttt{randomuser} API pattern.
    
    \item \textbf{Reviews Processing:} BookCrossing ratings (0--10 scale) and Amazon ratings (1--5 scale) are both normalized to the unified 10--100 scale used by BookSphere. Source provenance is preserved in the \texttt{source} field.
    
    \item \textbf{Data Enrichment:} The pipeline injects computed fields: ISBNs are cross-matched, bookshelves are populated (\\texttt{read} + \\texttt{want\_to\_read}), and pre-aggregated statistics are calculated (\texttt{stats\_per\_year}, \texttt{month\_score}, \texttt{popular\_reviews\_snapshot}, author \texttt{ratings\_count}/\texttt{sum\_ratings}).
    
    \item \textbf{MongoDB Export:} 4 JSONL files (\texttt{books.jsonl}, \texttt{users.jsonl}, \texttt{reviews.jsonl}, \texttt{authors.jsonl}) are generated for MongoDB ingestion via \texttt{mongoimport}.
    
    \item \textbf{Neo4j Export:} A second script reads the MongoDB JSONL output and generates 14 CSV files (5 node types + 9 relationship types) for Neo4j's \texttt{LOAD CSV} bulk import. Relationship inference is \textit{smart}: genre likes are derived from the user's actual reading history (top 3 genres), author likes from their bookshelf preferences, and book likes from high ratings ($\geq$80).
\end{enumerate}

\subsection{Deployment Scripts}
Three shell scripts automate database population:
\begin{itemize}
    \item \texttt{populate\_mongo.sh}: Single-node MongoDB import with index creation.
    \item \texttt{populate\_local\_cluster\_mongo.sh}: 3-node replica set import (\texttt{localhost:27017, 27018, 27019}).
    \item \texttt{populate\_neo4j.sh}: Copies CSVs to the import directory, clears the database, creates indexes on \texttt{mongoId}/\texttt{name}, and executes \texttt{LOAD CSV} for all nodes and relationships.
\end{itemize}

\textit{Data Variety:} By merging Amazon and BookCrossing, the dataset satisfies the multi-source requirement. \textit{Velocity:} Old reviews (pre-2024) are excluded from trending and monthly analytics, satisfying the temporal relevance requirement.
\section{Document Store: MongoDB}
MongoDB acts as the primary "Source of Truth" for the system. It stores the complete information about books, users, and reviews. The schema design prioritizes \textbf{Read Performance} through specific NoSQL patterns.

\subsection{Collections Overview}
The database \texttt{booksphere\_db} contains the following main collections:

\begin{enumerate}
    \item \textbf{books:} The central catalog entity.
    \item \textbf{users:} Stores authentication data and the user's library.
    \item \textbf{reviews:} Stores the full text of reviews. Linked to books and users via references.
    \item \textbf{authors:} Stores aggregated statistics about authors (e.g., total ratings).
\end{enumerate}

\section{Graph Store: Neo4j}
Neo4j serves as the secondary database optimized for social interactions and complex traversals. The graph model naturally represents relationships between Users, Books, Authors, Genres, and Reviews through typed edges.

\subsection{Node Types}
The Neo4j graph consists of the following node types:

\begin{enumerate}
    \item \textbf{User:} Represents registered users with properties: \texttt{mongoId}, \texttt{username}, \texttt{country}
    \item \textbf{Book:} Represents books with properties: \texttt{mongoId}, \texttt{title}, \texttt{year}
    \item \textbf{Author:} Represents authors with properties: \texttt{mongoId}, \texttt{name}
    \item \textbf{Genre:} Represents book genres with property: \texttt{name}
    \item \textbf{Review:} Represents user reviews with properties: \texttt{mongoId}, \texttt{rating}, \texttt{createdAt}
\end{enumerate}

\subsection{Relationship Types}
The following relationship types define the interactions and connections in the social graph:

\begin{itemize}
    \item \textbf{FOLLOWS:} (User)-[:FOLLOWS $\{$since: DateTime$\}$]->(User) - Social following relationship
    \item \textbf{POSTED:} (User)-[:POSTED]->(Review) - User authored a review
    \item \textbf{REFER\_TO:} (Review)-[:REFER\_TO]->(Book) - Review references a book
    \item \textbf{LIKES:} Multiple types:
    \begin{itemize}
        \item (User)-[:LIKES $\{$timestamp: DateTime$\}$]->(Book)
        \item (User)-[:LIKES $\{$timestamp: DateTime$\}$]->(Author)
        \item (User)-[:LIKES $\{$timestamp: DateTime$\}$]->(Genre)
        \item (User)-[:LIKES $\{$timestamp: DateTime$\}$]->(Review)
    \end{itemize}
    \item \textbf{WROTE:} (Author)-[:WROTE]->(Book) - Author wrote a book
    \item \textbf{BELONGS\_TO:} (Book)-[:BELONGS\_TO]->(Genre) - Book belongs to a genre
\end{itemize}

\subsection{Design Rationale}
The graph model was designed specifically to optimize the following query patterns:

\begin{itemize}
    \item \textbf{Recommendation Queries:} Multi-hop traversals to find books liked by followed users or written by liked authors
    \item \textbf{Social Network Queries:} Finding followers, followed users, and friend-of-friend relationships
    \item \textbf{Analytics Queries:} Calculating internationality indices by aggregating country properties across relationship paths
    \item \textbf{Influencer Detection:} Identifying users whose reviews receive high engagement through LIKES relationships
\end{itemize}

The \texttt{mongoId} property on User, Book, Author, and Review nodes serves as the primary key for cross-database synchronization, enabling efficient lookups when coordinating operations between MongoDB and Neo4j.

\subsection{Relationship Modeling Note}
Neo4j relationships are \textbf{not mapped} as Java entity fields. Instead, they are created and queried through custom \texttt{@Query} Cypher statements in the Neo4j repositories. This design decision was made because mapping relationships in Java caused memory issues: super-nodes like popular \texttt{Genre} nodes (connected to thousands of books) would load all adjacent nodes into the JVM heap upon access, leading to \texttt{OutOfMemoryError}. By using Cypher-only queries, we retrieve only the data needed for each specific use case.

\section{Polyglot Persistence Strategy}
\label{sec:consistency}

Maintaining data integrity between a Document Store and a Graph Database requires a strictly defined synchronization strategy. BookSphere prioritizes Eventual Consistency for high-frequency social features (Likes, Views) to ensure system availability, while enforcing Strict Consistency for critical Admin and Moderation operations.

\subsection{Error Handling Strategy}
To ensure robustness, we implemented a specific error handling flow:
\begin{itemize}
    \item \textbf{MongoDB Failure:} If the write to the primary DB fails, the operation aborts immediately. No try-catch block is used, allowing the \texttt{@Transactional} annotation to handle the rollback automatically.
    \item \textbf{Neo4j Failure:} If the write to MongoDB succeeds but Neo4j fails, a specific \texttt{try-catch} block intercepts the error and performs a manual rollback on MongoDB (deleting the just-created entity) to prevent "phantom data" and maintain consistency.
\end{itemize}
